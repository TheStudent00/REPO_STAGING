THE GAP, restated (see canon14_render.py's own header for the full
account): the general `concat` fold (unchanged since canon7_render.py)
recognizes exactly ONE syntactic shape as "this is really an extend" --
every sign-bit-replicate part's operand must be l.eq() to the concat's
own LAST part. Two independent things defeat that literal check and
were closed this lap:

  (i)  a leaf atom whose provenance resolves to a bare numeric
       IMMEDIATE (never in0/in1) is OPAQUE to z3's own simplify() --
       z3 has no numeric fact about an uninterpreted atom, so
       "Extract(63,8,atom_0)"-shaped dead padding around a flag byte
       gets rendered as real instructions instead of folding away.
  (ii) z3's own rewriting (NOT-distribution and, more generally, ANY
       rewrite that leaves a sign-bit-replicate part's source
       DIFFERENT from the concat's own trailing part, even though the
       two are PROVABLY bit-identical at the bit that matters) defeats
       a purely syntactic recognizer.

A THIRD defect was found tracing sighting (c) to ground and fixed in
the same lap, "fix a cause at first observation" (AgentMemory): a z3
`bvnot` node whose operand is a TRUE 1-bit-wide node (a boolean 0/1
value, not a general bitvector) was rendered with a literal `not`
instruction -- bitwise-flips all 8 bits of the byte register the value
actually lives in (0x00 -> 0xFF = 255, not the logical negation 1).

    cmp $0,%r11d                    flags = compare(%r11d, 0)
    sete %r10b                        %r10b = flags.equal ? 1 : 0
    or %r10b,%al                        %al = %al | %r10b
    xor $1,%al                            %al = %al ^ 1
    movzx %al,%eax                          %eax = zero_extend(%al)
    ret                                       return %eax

THE FIX THAT CLOSED THIS ONE (FIX (iii), see canon14_render.py's own
`gen14`): the z3 tree here is `Concat(0, ~(If(a==0,1,0) |
If(b==0,1,0)))` -- De Morgan's own reading of `(a!=0) & (b!=0)`. The
`bvnot` node's operand measures z3-node-width 1 (an OR of two
If-booleans) -- the OLD `bvnot` branch (unchanged, still reached by
delegation for every OTHER shape) rendered it with a literal `not`
instruction, bitwise-flipping the WHOLE byte register the value
occupies (0x00 -> 0xFF = 255) instead of the single bit that is
actually meaningful. Measured counterexample this defect produced,
BEFORE this fix, on the collapsed-but-still-wrong candidate:
seed_rdi=4294967295, seed_rsi=18446744073709551615 -- real answer is 1
(both nonzero), the `not`-based candidate answered 255. THE FIX: a z3
node of TRUE WIDTH 1 can only ever be 0 or 1 by construction, so
"bitwise NOT of this node's one meaningful bit" and "logical NOT of a
canonical 0/1 byte" are the SAME operation; `xor $1,<8-bit dest>`
implements it correctly (flips only the bit that matters, leaves the
already-clean upper 7 bits alone). Reuses the identical instruction
canon13_render.gen_bool's own `not` case already uses, for the same
reason, one level up in the dispatch.

INSTRUCTION COUNT: ~50 (BEFORE, bit-serial) -> 20 (AFTER) -- the
32-copy sign-bit-replicate run collapsed to the single `movsxd
%r8d,%r8` at line 14, exactly the mechanism `_maximal_extend_fold`
(canon14_render.py) exists to do: z3 PROVED
`Concat(Extract(31,31,atom_0) x32, Extract(31,8,atom_0), 0,
If(...)|If(...)) == SignExt(32, rest)` for the maximal head run before
this candidate was ever assembled, so the collapse is not a heuristic
guess -- it is checked, per candidate, before being used.

NORMALIZER-shaped gap, out of a renderer fix's charter; diagnosed here

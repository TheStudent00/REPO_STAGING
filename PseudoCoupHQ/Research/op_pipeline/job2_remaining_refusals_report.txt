DIAGNOSIS (evidence class: forced by construction, direct read of
swift/op_296's own job2_pairing_candidate_text): the rendered sign
test for `a` (Int32) is

    mov $0,%r11; mov %rdi,%r9; and $-1,%r9d; cmp %r9,%r11; setg %r10b

-- i.e. `0 >s zero_extend_64(a)`. A 32-bit value ZERO-extended to 64
bits is NEVER negative as a 64-bit signed quantity (its bit 63 is
always 0), so `0 >s zero_extend_64(a)` is ALWAYS FALSE regardless of
`a`'s own sign -- structurally unable to express "is the 32-bit value
`a` negative" at all. Real ship code tests this with `test %edi,%edi;
sets` (the 32-bit sign flag, direct). This is a THIRD, DISTINCT defect
from both JOB 1's (bit-serial reconstruction) and JOB 2's (call-site
pairing) -- somewhere in canon12_normalize.py's wide-arithmetic model,
the 32-bit signed operand's own SIGN acquisition is built as a 64-bit
comparison against a ZERO-extended (not sign-extended) copy of itself,
which cannot ever be true. NOT FIXED this lap -- found while closing
out JOB 2's own target set, reported per the evidence doctrine rather
than left unexplained or forced to a false converge. A follow-on
should locate where canon12_normalize.py builds this specific
sign-test sub-expression for a mixed-width signed/unsigned comparison
and confirm whether it is a sign-extend that got typo'd to a
zero-extend, or a genuinely different (and here, wrong) formula.

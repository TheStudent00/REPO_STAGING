## Entry 2026-07-24 — The extraction system (the owner's cornerstone)

Dominant intentions exist as battle-tested code in the dominant
language's compiler/core. Extract the logic chain (program slice),
transpile via PCv3 into Python, mount in the hub — canonical
semantics DERIVED from ground truth, not reauthored.

Chains bottom out in three strata, each with a different move:

- **pure library logic** (e.g. i64::div_euclid, ~6 lines of Rust)
  → transpile the code
- **compiler desugarings** (e.g. match → decision trees)
  → transpile; the output is a rule
- **intrinsic-bottomed** (e.g. wrapping_add → machine op)
  → no code to extract; chain terminates at a spec pointer into
  the basis layer

Extraction requires CST/Ledger awareness: operators inside the
slice carry source-language semantics (Rust `/` must become
trunc_div, NOT Python `/` — a class-1 divergence inside the
extraction itself).

Mounting levels: (1) module — stock CPython, borrows spelled as
calls; (2) interpreter insertion — forked CPython, real syntax,
maintenance bill. The chain is identical; only the mounting
differs.

## Entry 2026-07-25 — The routing-logic insertion (settled design)

### The problem this solves (the owner's account)

The wanted artifact was a Dict: key = high-level operator,
value = the IR opcode sequence it compiles to. No compiler CONTAINS
that Dict — the mapping is generated by routing logic smeared
across passes, switches, and variable-dependent branches.
Deterministic, but not isolable as a table.

Solution: do not extract the table. Extract the TABLE-GENERATOR.
Transpile the routing logic itself into Python and run it there.
Python then produces the target language's IR opcodes and arch
opcodes by executing the target compiler's own logic.

### Pipeline

```
hub script:      a r./ b               high-level spelling
      |
      |  registered operator invokes
      v
transpiled MIR routing logic           running IN Python
      |
      v
CLIF ops                               Rust's own IR vocabulary
      |
      |  transpiled encoding logic (also inserted)
      v
x86-64 bytes                           what rustc would have emitted
      |
      v
mounted + called                       result lands in a RustI64 cell
```

Not an approximation of a Rust object — the semantics are computed
by Rust's own code at every step.

### Why Cranelift, not LLVM

rustc default: HIR → MIR → **LLVM** → arch. LLVM is a C++
continent; slicing it is an invasion, not an extraction.
rustc_codegen_cranelift is pure Rust: MIR → CLIF → x86-64
directly. So an all-Rust chain exists end to end. Wrinkle:
Cranelift's lowering rules are written in the ISLE DSL which
GENERATES Rust — cut the slice from the generated Rust (plain
code).

### The adapter: three rings

Invariant: **the slice's logic is never adapted; only its severed
edges are re-anchored.**

- **input ring** — rustc routing functions take context objects
  (FunctionCx, builder, TyCtxt), not (a, b). Stand-ins carry only
  the fields the slice touches. Principled anchor: **the Ledger
  plays the type context** — it already holds what TyCtxt would
  answer. (Precedent: RyuJIT experiment's RegSet/PatchpointInfo
  stand-ins.)
- **invocation ring** — the router runs at hub COMPILE time, so
  ceval is the wrong door. Stock-Python door: an import hook
  (intercepts a module between AST and bytecode), which finds
  qualified operators on Ledger-typed operands, invokes the router
  there, and plants the produced bytes + call stub. A forked
  compile.c calling the router is the deeper later version; the
  hook measures everything except the fork.
- **output ring** — mmap-and-call: ask the OS for a page, write the
  bytes, mark it executable, call it via ctypes. (That is the whole
  of "JIT" — four steps, no magic.)

### RustI64: crossing per border, not per operation

```
RustI64
	an aligned 8-byte cell (Rust's i64 layout)
	behind a Python object handle.
	born from:  RustI64(literal)   — the ONE inbound conversion
	dies into:  int(x) / print     — the ONE outbound conversion
```

The compiled code receives POINTERS TO CELLS, not marshalled
values. `((a r.+ b) r./ c) r.% d` stays in Rust representation
throughout; PyLong appears exactly twice regardless of chain
length.

- This is the first RUNNING instance of a border-lattice verdict:
  RustI64 entering an unqualified Python expression is class-1,
  convertible, explicit spelling `int(x)`, never silent.
- Two mounting levels as always: PoC = ctypes-backed aligned
  buffer (pointers are real); fork = a lean C type PyRustI64. The
  compiled code cannot tell the difference — the point.
- f64 held back until an extracted chain touches floats (IEEE754
  is uniform per the basis audit, so nothing new to solve).

### Scope + acceptance

Slice: MIR BinOp Div-family routing for i64 (cranelift codegen) +
post-ISLE generated encoding for that instruction family.
Acceptance: (a) result grid byte-identical to native rustc;
(b) disassembly of our produced bytes matches Cranelift's own
output for the same function.

# 1. What the objects are

- **an arch-unit** -- one compiled function body, carved out of a
  shipped object file with the pipeline's own objdump reader
  (`lane_gen.extract`).
- **a pool entry** -- the set of arch-units, across languages, that
  were proved to answer the same for every input
  (`~/Programming/PseudoCoupHQ/Research/op_pipeline/the_pool5.json`).
- **a term** -- one arch-unit written as a z3 expression; the entry's
  **layer-5 text** is that expression printed by one fixed rule.
- **an x unit** -- a member of a pool entry in c, go or swift whose
  entry has NO rust member: nobody has built the rust arch-unit that
  answers the same. Task o1's length-one map
  (`~/Programming/PseudoCoupHQ/Research/oracle/cross_construction/cross1_length_one.json`)
  names them, under the pair keys `rust|c`, `rust|go` and `rust|swift`.
- **an emulation** -- a rust function whose body is that entry's term
  written in rust's own operations over rust's holders, produced by
  the ONE renderer in
  `~/Programming/PseudoCoupHQ/Research/oracle/cross_construction/emulation/rust/rust_render.py`
  (`RustRenderer`), which DERIVES from task o7's `emulate.Renderer` and
  overrides one method per row of the coverage table. A term the
  renderer cannot render is refused by cause and no source is written.
- **the coverage table** -- the object log 221 section 3 names: the
  term language's operators as rows, the target languages as columns,
  each cell saying whether the target has a direct operator for that
  row, needs a named idiom, or has no construction at all. Beside it,
  the sorts: task t101b's 32 holders as each target spells them.
- **the collapse test** -- compile the emulation at the flags the whole
  rust corpus was built with, carve the body, and ask the same three
  questions o7 asked of c: Q1 are its bytes bytes some rust unit
  already has; Q2 is its printed term the entry's text; Q3 does the
  solver prove it answers as the x unit does for every input. On task
  o2's single-opcode rows, one more: Q0, does the chaff-stripped body
  come back as exactly the row's own arch opcode.

# 2. What was done and what came back

Task o7 asked whether a c emulation of another language's unit gets
lowered back into a c unit the corpus already has. This task asks the
same of a second compiler, and adds the question the emulation route
needs answered before it can be a route at all: what does the term
language COST in each target -- which of its operators the target
spells directly, which need a named construction, and which it cannot
express.

The coverage table was built first, before any emulation ran, and its
rust column was measured rather than recalled. Four small lanes
compiled one rust function per question at the rust corpus's own ship
flags and read the emitted body back with the pipeline's objdump
reader. Three of those measurements changed what the renderer had to
write. Plain arithmetic wraps at the ship flags but branches to a panic
routine at `debug-assertions=on`, so the renderer writes the wrapping
method and does not depend on a flag. Division checks a zero divisor in
BOTH builds -- that check is not a debug assertion -- and the signed
forms check the extreme case as well, so division needed an idiom; the
one that works is an unreachable hint under exactly the conditions the
machine's own divide leaves undefined, and under it rustc emits the
bare `div` and `idiv`. The plain float-to-integer cast saturates in
rust rather than truncating, so it needed an idiom too. Against those
twenty idioms there is exactly one hole, and it is a sort rather than
an operator: rustc 1.96.1 has no 16-bit float holder, so a term whose
arrival or answer is a half-width float has nowhere to land.

Then the run. Of the 1,175 pool entries that have a c, go or swift
member and no rust member, 561 carry a layer-5 text the parser
round-trips; 400 of those were drawn uniformly and emulated. 320
rendered, and every one of the 320 compiled -- rustc refused nothing.
243 were proved equal to the x unit, and 41 more once every byte-wide
or halfword-wide argument is taken to arrive already widened to the
register, for 284 of 320.

At the byte level the answer is again mostly no, and again the control
is what makes that readable. 2 of 320 emulations came out carrying
bytes an existing rust unit already has. Take 40 entries that DO have a
rust member, render from that member's own term, and rustc lands back
on that member's own bytes 27 times in 39 -- a much higher ceiling than
clang's 14 in 33 on the same experiment in task o7 (log 218 section 4),
so rustc's lowering of the renderer's long nested source is more
predictable than clang's, not less.

The sharpest result is task o8's question asked of rust. Of the 107
single-opcode rows of c, go and swift that rendered and compiled, 99
came back as exactly the row's own arch opcode. The two that landed
elsewhere are both go two-register sums, where rustc chose `lea` over
`add` -- the same substitution clang made in task o8 (log 220 section
6.2). The six that did not collapse are all c rows whose term joins a
32-bit answer into a 64-bit holder, so the emulation carries the join
as well as the operation.

**GLOSS**, one line per rule the renderer needed, each pointing into
the block above:

- **Wrapping arithmetic.** `plain_sum_u32` and `wrapping_sum_u32` emit
  the SAME body, `lea (%rdi,%rsi,1),%eax; ret`, at the ship flags,
  because the corpus's rust ship build carries
  `-C debug-assertions=off` and rustc's overflow checks follow that
  flag. At `debug-assertions=on` the plain form emits a branch to
  `panic_const_add_overflow` instead (lane o11_l1's own
  `debug_assertions_on` field, in
  `~/Programming/PseudoCoupHQ/Research/oracle/cross_construction/emulation/rust/rust_facts.json`).
  So the SHIP FLAGS WRAP, and the renderer still writes
  `wrapping_add`, because a rule that depends on a flag is not a rule.
- **Shifts.** `plain_left_shift_u32` and `wrapping_left_shift_u32` both
  emit `shl %cl,%eax`, which masks the count to the width -- the
  MACHINE's rule. The term's rule is that a count at or above the
  width answers with the fill, so the renderer writes the guard out,
  exactly as the c renderer does. At `debug-assertions=on` the plain
  shift branches to `panic_const_shl_overflow`.
- **Division.** `plain_quotient_u32` carries `test %esi,%esi; je ...`
  and a call to `panic_const_div_by_zero` AT THE SHIP FLAGS -- the zero
  check is not a debug assertion. `plain_quotient_i32` carries that
  check AND the signed-extreme check
  (`lea -0x80000000(%rdi),%ecx; or %eax,%ecx; je ...` into
  `panic_const_div_overflow`). `hinted_quotient_u32` removes the first;
  `hinted_quotient_i32` shows that `core::hint::assert_unchecked` does
  NOT remove the second; `unreachable_quotient_i32` does, and emits
  `mov %edi,%eax; cltd; idiv %esi; ret` -- the bare signed divide.
  That last spelling is the renderer's rule for all four division
  rows.
- **No implicit widening.** `widen_u8_to_u32` is `mov %edi,%eax` and
  `sign_extend_i8_to_i64` is `movslq %edi,%rax`: both need an explicit
  `as` in the source, and the sign-fill is chosen by the type of the
  cast, not by the operator.
- **128-bit holders exist.** `sum_u128` is
  `mov %rdi,%rax; add %rdx,%rax; adc %rcx,%rsi; mov %rsi,%rdx`, the
  two-register pair, so `u128` and `i128` are real holders under
  `extern "C"`.
- **Float to integer saturates.** `saturating_f64_to_i64` (plain `as`)
  is seven instructions with a not-a-number case;
  `truncating_f64_to_i64` (`to_int_unchecked` in `unsafe`) is the bare
  `cvttsd2si %xmm0,%rax`. c's plain cast gets the second for free, so
  this row is an idiom in rust and direct in c.
- **The one hole.** `float16_holder` and `float128_holder` are both
  refused: `error[E0658]: the type \`f16\` is unstable`.
- **The arrival width.** `wide_arrival_u8` computes on the whole
  `%esi` and `%edi`, so rust's `extern "C"` callee assumes the caller
  widened a narrow argument, exactly as c's does. That is why task
  o7's caller-extension re-pose applies here unchanged.

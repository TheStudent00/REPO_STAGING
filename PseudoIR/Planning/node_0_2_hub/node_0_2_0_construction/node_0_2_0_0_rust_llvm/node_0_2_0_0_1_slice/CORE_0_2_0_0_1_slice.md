## definition

cutting rust's semantics out of the transpiled compiler

## the chain we are cutting from

compiling `a + b` in rust to machine code passes through three
stages. we need all three inside the hub, so each is its own job.

1. **rust source becomes llvm ir.** rustc reads `a + b` and writes
   one line of llvm's own instruction language: `add i64 %a, %b`.
   still language-independent, no cpu chosen yet. the rustc code
   that does this is `rvalue.rs`'s BinOp routing.
2. **llvm ir becomes a machine instruction.** something decides that
   `add i64` on x86-64 is the instruction `addq`. this is the
   IRMapping stage, and it is the one with no answer.
3. **the machine instruction becomes bytes.** `addq %rsi, %rdi`
   becomes `48 01 f7`. llvm's `X86MCCodeEmitter.cpp` does it, one
   such file per cpu architecture.

## why stage 2 is the hard one

the order is the same for every stage: transpile the compiler's
source, then slice the intention-bearing part out of it, then insert
the slice. stage 2 is not hard to transpile. it is hard to SLICE.

llvm implements the decision as an interpreter running a compiled
program, not as named functions:

- `SelectCodeCommon`, 1,145 hand-written lines, is a small virtual
  machine.
- `MatcherTable[]`, about 375,000 lines, is a generated byte array.
  it is that virtual machine's program — the patterns, compiled into
  bytes, not source anyone wrote.
- plus 210 hand-written x86 special cases in `X86ISelDAGToDAG.cpp`.

so the difficulty is in two places:

- **no seam to cut on.** the slicer selects the logic that carries
  an intention. here "which instruction implements this operation"
  is not in a function — it is spread through the bytes of an array
  that only `SelectCodeCommon` can read. take less than all of it
  and you have taken nothing.
- **scale.** an array literal of 375,000 lines parses into that many
  nodes and that many ledger records. this is the same unresolved
  scale problem recorded at the transpile stage.

the previous plan asserted the table was "NOT transpilable by the
1:1-function strategy". that phrasing is not ours and is not
checked — the transpiler works a file at a time from tree-sitter
output, and tree-sitter parses an array literal fine. the real
obstruction is sliceability and scale, above. **unverified**: nobody
has run the transpiler at `MatcherTable[]` to find out.

## the three ways out, none chosen

- **hand-map**: the hub emits a handful of operations — integer
  arithmetic. write the small table by hand, one entry per
  operation, and make everything else fail loudly. cheap and
  cuttable.
- **transpile and take the whole engine**: carry `SelectCodeCommon`
  and `MatcherTable[]` across entire. complete, but the hub then
  holds llvm's pattern-matching engine rather than the intentions,
  which is against what the hub is for.
- **call llvm at run time** through llvmlite instead of extracting
  anything. avoids the work; adds a permanent dependency on the
  compiler this project exists to absorb.

the deciding evidence comes from doing stage 1 first: count how many
distinct operation kinds the hub actually emits. if it is a handful,
hand-map is obviously right and the other two wait for a real need.
**the owner decides, after that count exists.**

## blocking

this node is `blocked`, and the block is specific: stage 2 has no
answer, so the whole chain cannot close. it does NOT block stages 1
and 3 — and stage 1 is what produces the count that unblocks it.

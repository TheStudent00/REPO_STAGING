## §1. What the objects are, one sentence each, in relation

- A **single-opcode row** is one row of task o2's
  `single_opcode_groups.<lang>.narrow`, for the five compiled
  languages (c, cpp, go, rust, swift) — the same population task o8
  (log 220) used.
- A **proved row** is a single-opcode row whose `example_unit_id`
  reads `term_state == "TERM"` in `the_pool5.json` — 243 of 259, the
  same 16 c/cpp `call` rows (wide-integer runtime callees:
  `__divti3`/`__udivti3`/`__modti3`) task o8 found and skipped, for
  the same reason.
- A **holder** is one of t101b's 32 (class, width) reading buckets
  (log 217); this task reads a unit's holders directly off
  `types101_entry_holders.json`, never re-derives them.
- A **signature** is one (parameter_holders tuple -> result_holder)
  pair attested by at least one member unit of a proved row — the
  join task o8 did not need and log 221 named as missing.
- A **family** is one entry of `the_families5.json`'s `families` list
  (a machine-form cluster of (language, grammar-operator, arity)
  nodes joined by shared pool entries); membership is read off a
  node's own `units` list, never off the operator token.
- A **guard-outcome row** is a canon40 ledger row with
  `block == "GUARD"` — in every one of the 23,942 GUARD rows this
  task streamed, `produced_by.kind == "flag_pair"` (§4 below); no
  other kind ever carries that block in this corpus.
- The **262-row deliverable-1 table**, the **25-mnemonic reading-kind
  table**, and the **162-mnemonic guard-partition table** are three
  renderings of the same three joins above, at three different keys
  (mnemonic+signature, mnemonic, mnemonic).

The population is identical to task o8's: `single_opcode_units.json`'s
narrow rows for c/cpp/go/rust/swift (259 rows), filtered to the ones

```

pool = json.load(open('Research/op_pipeline/the_pool5.json'))
unit_to_termstate = {}

    for m in e['members']:

langs5 = ['c','cpp','go','rust','swift']
```

## §9. Mechanisms, and one bug caught mid-task

**Bug, caught before this task's first census run was reported.** The
first pass (`o9_l1_census.sh`) computed sign-sensitivity and
reading-blindness from ANY class difference at matching widths (e.g.
`add` vs `addsd` shared family F0004 and a width signature `8,8 -> 8`
purely because int-add and float-add happen to share a family node
and a width — an int/float distinction, not a signed/unsigned one),

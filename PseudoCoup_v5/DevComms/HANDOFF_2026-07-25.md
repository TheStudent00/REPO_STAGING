# 1. What this project is

PseudoCoup: write applications once in disciplined Python (the
"hub"), render to any of 12 target languages losslessly. PCv5 is the
experimental stage proving the mechanism; PCv7 is the polished goal.

The specific thing PCv5 set out to prove, and did:

> A compiler's routing logic — the mapping from high-level operator
> to IR opcode to machine opcode — can be **extracted from a real
> compiler and executed inside Python**, so the hub computes target
> semantics using the target compiler's own code rather than a
> reimplementation.

The motivating problem (the owner's, from the Go compiler): the mapping you
want is a `Dict` — key = high-level operator, value = IR opcode
sequence — but **no compiler contains that Dict**. It is generated by
routing logic smeared across passes and branches. So: do not extract
the table. Extract the **table-generator** and run it.

## 2.1 The extraction pipeline (Research/rust_routing/)

Working end to end. A `.pc` hub module using qualified operators is
executed by machine code that a real compiler's own logic produced:

`demo.pc` contains `a r./ b`; each step feeds the next:

1. import hook rewrites the spelling (`pc_import.py`) — no parser
   surgery.
2. the Ledger answers the type question (`ledger.py`).
3. slice 1, MIR routing (`slice_mir_routing.py`) → CLIF `sdiv`.
4. slice 1.5, ISLE lowering (`slice_lowering.py`) → `cqto`+`idiv`.
5. slice 2, encoding (`pc_vocab`, machine-transpiled) → bytes.
6. output ring mounts and runs the bytes, mmap+mprotect+ctypes
   (`output_ring.py`).
7. the result lands in a `RustI64` cell (`rust_cell.py`).

**Verified:** `./verify_all.sh` — four suites ALL PASS, plus a
130-row arithmetic grid checked against native `rustc -O`
(byte-identical at the 81-row stage; extended to 130 rows covering
`-1` divisors and full unsigned range, passing an independent
semantic check).

Key demonstrated result: `-7 r./ 2 == -3` (truncating, the target's
semantics) while Python's own `-7 // 2 == -4`. The divergence is
resolved by *executing the target's arithmetic*, not emulating it.

# 3. Findings that constrain design (all measured)

## 3.1 Generated code is transpilable; hand-written tables are not

| source | lines | unclassified | shape |
|---|---|---|---|
| Cranelift `assembler.rs` (generated Rust) | 14,876 | **0** | 1071 readable per-instruction fns, 12 node kinds |
| LLVM `X86GenDAGISel.inc` (generated C++) | 375,884 | 357 | **~99.5% one opaque `MatcherTable[]`** |
| LLVM `X86GenInstrInfo.inc` | 162,160 | 92 | ~87% struct/enum/string tables |

The matcher table is consumed by a hand-written bytecode VM —
`SelectCodeCommon`, **1,145 lines interpreting 173 distinct table
opcodes** (`OPC_CheckOpcode`, `OPC_MoveChild`, …). Using LLVM's
selector means transpiling that VM and carrying the table as data.

`X86ISelDAGToDAG.cpp::Select()` additionally has **210 hand-matched
C++ cases** as an escape hatch — `IDIV64r` is one, which is why the
div path was traceable by hand.

## 3.2 LLVM's encoder is hand-written, not generated

X86 **never runs `-gen-emitter`**. `X86MCCodeEmitter.cpp` (2,033
lines) is 100% hand-written — architecturally opposite to Cranelift,
which generates readable encoders and hand-writes only support.

## 3.3 C++ ingress is tractable; pointers are a non-issue

Measured across `X86MCCodeEmitter.cpp`, `SelectionDAGISel.cpp`,
`X86ISelDAGToDAG.cpp`: pointer-expression derefs — 0, 0, 0;
`memcpy`/`memset`/`reinterpret_cast`/`new[]` — 0, 0, 0.

Every `->` is object navigation (free in Python — Python objects are
references). Every flagged "pointer arithmetic" site is an integer
counter (`CurOp++`). **No memory-model simulation is needed.**
`X86MCCodeEmitter.cpp` has 0 templates, 1 macro, 2 classes, 1 STL
use, 1 lambda; the bulk is switches and bit arithmetic — i.e. the
same shape as the Rust support layer we already transpiled.

The one real node rule: `f(x++)` splits into two statements, valid
because the parameter is by-value and there are zero multi-increment
expressions (both verified). The transpiler **asserts** these rather
than assuming — this is divergence class 3 appearing inside our own
tooling.

## 3.4 The ISA is the ISA

LLVM's REX line and Cranelift's are character-identical:

```cpp
emitByte(0x40 | W << 3 | R << 2 | X << 1 | B, CB);   // LLVM
0x40 | (w << 3) | (r << 2) | (x << 1) | b            // Cranelift
```

And our produced div/rem/mul bytes appear **verbatim inside gcc -O2's
output**. Three independent compilers agree because all three
transcribe Intel's manual. What we extracted is the ISA, not any
one compiler's opinion.

Real difference found out-of-domain: LLVM's `modRMByte` does **no
masking** and relies on `assert()`; Cranelift masks (`& 3`, `& 7`)
with `debug_assert!`. In release both guards vanish, so out of domain
LLVM's formula can exceed a byte while Cranelift wraps. Inside the
asserted domain they are identical.

# 4. Decisions taken (and by whom)

| decision | choice | rationale |
|---|---|---|
| emit `.py` files vs in-memory | **files** (the owner) | the emitted vocabulary is PseudoCoup's *stability layer*, versioned against the source compiler — a churn guard, traceable |
| whole vocabulary vs on-demand | **whole** (the owner) | grammar is 12 node kinds; running the same tool over 1071 costs output size, not effort |
| generated output vs meta-generator | **generated output** (the owner, green-lit) | same rule ISLE taught: cut from generated code, never the DSL. Version-pinning is the point, not a defect |
| polyfill depth | **uniform, no exemptions** (the owner) | mixed depth makes an unwrapped node ambiguous between "proven safe" and "tool missed it" |
| cuts | **carry reachability invariants, asserted** | a cut fails loudly at its site rather than emitting wrong bytes |
| J3 run-time metaprogramming | **egress-coverage analyzer, not a ban** (the owner) | warn at the *invalidated proof sites*, not only the mutation site |
| determinism | **no timestamps in output** | regeneration byte-identical, so `git diff` shows real changes only |

# 7. Forward plan — LLVM only

**Goal (the owner, 2026-07-25):** a complete solution for the **Rust
language** first, since its intentions are the most dominant
(satisfier analysis: Rust satisfies rows A/C/D/G — suspension,
optionals, pattern matching, scoped cleanup). Complete means: for
each slice we need, a mapping down to machine code **across all
architectures**, via LLVM, which is what rustc actually uses and what
covers every architecture that matters.

## 7.1 What "complete for Rust" requires

| stage | produces | lives in |
|---|---|---|
| MIR routing | MIR ops | `rustc_codegen_ssa/src/mir/rvalue.rs` |
| LLVM IR building | LLVM IR opcode (macro-generated: sdiv → `LLVMBuildSDiv`) | `rustc_codegen_llvm/src/builder.rs` |

Back half is C++, per-architecture, and now proven transpilable at

## 7.2 Recommended sequence

**REORDERED 2026-07-27 (the owner).** The first draft put the aarch64
encoder first. That misread the role of the Cranelift-derived
vocabulary: `pc_vocab/` is an x86-64 oracle, so x86-64 is the ONE
architecture where every LLVM-derived piece can be byte-checked
against an independent extraction. Establish the LLVM chain on
x86-64 first, where disagreement is detectable; go to aarch64 only
once the chain's shape is proven. Detail and file layout:
`plan_llvm_rust_2026-07-27.md`.

**Step 1 — complete the LLVM x86-64 encoder.** Extend the Phase 2
slice (modRM/REX/SIB/REX-prefix/emitByte) to the full per-instruction
emission path of `X86MCCodeEmitter.cpp` (`encodeInstruction`, opcode
and immediate flow). Acceptance: bytes identical to the `pc_vocab`
oracle for every instruction both cover, plus the grid vs native
rustc.

**Step 2 — the MIR→LLVM IR front half.** Transpile
`rvalue.rs`'s `BinOp` routing plus the `math_builder_methods!` macro
expansion. This is Rust, and the grammar is one we have already
handled. Acceptance: emitted LLVM IR opcode matches
`rustc --emit=llvm-ir` for each hub operator.

**Step 3 — the LLVM-IR→ISD slice.** The `SelectionDAGBuilder.cpp`
visit arms for the opcodes the hub emits (`visitSDiv` at :3794 is
already traced). Small, per-opcode, same C++ grammar as step 1.

**Step 4 — decide on the selector.** Between step 3's output (an ISD
node) and step 1's input (a machine instruction) sits the ISel gap:
the 1,145-line VM plus the table. Options, in cost order:
  a. hand-map the small set of opcodes the hub actually emits
     (integer arithmetic is a handful) — cheap, honest, stubbable
  b. transpile `SelectCodeCommon` and carry `MatcherTable[]` as data
     — the full solution, expensive
  c. use llvmlite as a reference oracle rather than extracting
Do NOT pre-commit; price it after steps 1–3.

**Step 5 — all-LLVM chain, then slice dominant intentions.** Run the
existing `demo.pc` chain with every stage LLVM-derived (Cranelift
pieces retired from the running path, kept as oracle). Then slice the
next dominant intentions per the satisfier rows.

**Step 6 — aarch64, then further architectures.** Apply
`transpile_cpp.py` to `AArch64MCCodeEmitter.cpp` — *survey its
grammar first*. Acceptance: bytes match native
`rustc --target aarch64-unknown-linux-gnu` (no oracle exists there;
native rustc is the only ground truth). The encoder work is
per-architecture; the front half is shared.

## 8.1 Philosophy settled 2026-07-27

Four positions were clarified in conversation. Each one closed
something this report previously listed as open. They are recorded
with their reasoning so a future contradiction is checkable.

### The hub dominates; egress shortfalls are recorded, not designed around

An earlier draft defined the basis layer as "what every one of the 12
egress languages must supply natively." That is wrong, and it inverts
the dominance rule.

- Intent is captured at ingress and lives in the **Ledger**. A source
  declaring a hash map records that type; a source declaring a list of
  pairs records a different one. The choice of data structure is the
  choice of complexity class, and the type identity already carries it.
- The hub satisfies that intent by **feature insertion** — the
  mechanism proven in this project by inserting Rust's routing logic
  into CPython.
- If a target language has no fast retrieval, the rendered program
  has no fast retrieval. That is a **recorded shortfall of the
  destination**, not a constraint on the hub. Improving it later by
  feature insertion into that destination is possible and is not
  scheduled.
- Consequence: **"performance-primitive completeness" is closed.** It
  was a question that only existed under the destination-first
  framing.
  Hashing, the executor, and the string builder need no adjudication;
  their intent is Ledger data either way.
- **Priority statement (the owner):** ingress into the hub is the current
  highest priority.

### Tail calls: a hub transformation, not a basis member or a divergence class

A tail call is a call whose result is returned directly with nothing
pending afterwards, so the current frame has no reason to survive it.
This was previously filed as a performance-primitive candidate, then
as a divergence class. Both were wrong — it needs no bucket, because
the hub can perform the transformation itself and every target
language has a loop.

**Case 1 — self-recursion. Rewrite to a loop. Costs nothing.**

```python
def count_down(n, acc):            # dies at n=1000 on CPython
    if n == 0:
        return acc
    return count_down(n - 1, acc + n)
```

```python
def count_down(n, acc):            # constant stack, same answers
    while True:
        if n == 0:
            return acc
        n, acc = n - 1, acc + n
```

The rebinding must be **simultaneous**. `n = n - 1` followed by
`acc = acc + n` reads the already-decremented `n` and returns the
wrong sum. This is what Kotlin's `tailrec` compiles to.

**Case 2 — mutual recursion. A wrapper (the owner's proposal). Costs one
object allocation per step, and covers what case 1 cannot.**

The function returns a *description* of the next call instead of
making it. A driver loop performs the calls one at a time, so exactly
one frame exists at any moment.

```python
class Call:
    def __init__(self, fn, *args):
        self.fn = fn
        self.args = args

def run(result):
    while isinstance(result, Call):
        result = result.fn(*result.args)
    return result
```

```python
def is_even(n):
    return True if n == 0 else Call(is_odd, n - 1)

def is_odd(n):
    return False if n == 0 else Call(is_even, n - 1)
```

The driver never inspects *which* function it is calling, which is
why mutual recursion works unchanged.

**Two preconditions, both required, both visible in the source:**

- Every recursive call is in tail position. `return 1 + f(x)` fails —
  the addition is pending, so the frame must survive and there is no
  return value to hand the driver.
- The calls form a linear sequence: one step leads to at most one next
  step. `return fib(n-1) + fib(n-2)` fails twice — two calls, and an
  addition waiting on both.

| shape | method | cost per step |
|---|---|---|
| self-recursive | rewrite to `while` | nothing |
| mutually recursive | wrapper + driver | one allocation |

The shape is decidable from the source, so the hub picks without
asking. Both the rewrite and the wrapper are ordinary hub code and
egress to all 12 destinations like anything else.

### Memory: three separate questions, previously conflated

Detail in [open_issues.md](file://~/Programming/PseudoCoup_v5/DevComms/open_issues.md) Issue 3.

- **Ingress** — does the C++ we pull into the hub need a memory model?
  **No, measured**: zero pointer-expression derefs and zero
  `memcpy`/`memset`/`reinterpret_cast`/`new[]` across the three LLVM
  files (section 3.3).
- **Egress** — can pointer infrastructure be rendered into a language
  with no addresses? **Yes, priced, dormant**: simulate the address
  space as a byte array, pointer becomes an integer index. Emscripten
  is the existence proof. The price is that output stops being
  idiomatic. Nothing currently egresses pointer-bearing source.
- **Emitted instructions** — will we emit x86 memory operands
  (`add rax, [rbx+8]`)? Unreachable today by caller invariant, which
  the stub asserts. Becomes reachable when register allocation spills.
  Register allocation is not scoped.

### Vocabulary

**CORRECTED 2026-07-27 (the owner).** An earlier draft coined "egress
language" as a category name. That was wrong: egress/ingress name a
*direction relative to a perspective*, not a kind of language, and
source/target name *roles relative to a perspective*. Transpiling
Rust into Python is an egress from Rust (source) and an ingress to
the hub (target); the same hub is later the source when rendering
out. Freezing one perspective into a noun destroys that.

The settled terms:

- **target language** — one of the 12 languages the hub renders to.
  ("target" previously did double duty; the ambiguity is resolved by
  the next entry, not by inventing a new word.)
- **architecture** — an instruction set (x86-64, aarch64). Was also
  called "target".
- **egress / ingress** — directions, always relative to a stated
  perspective. Never a category name.
- **slice** — extracted from a compiler. Was called "cut".
- **stub** — deliberately excluded, with an asserted reachability
  invariant. Was also called "cut".

Swept 2026-07-27 in this file and `open_issues.md`. The remaining
documents (`dev_plan_log.md`, `project_state.md`, the four
`Research/*/README.md`) still carry the old words.

# 10. Standing rules

- Measure, do not estimate. Every number comes from a command run.
- Uniform polyfill wrapping; no proof-as-exemption.
- Cuts carry reachability invariants and assert them.
- Emitted artifacts are the stability layer: deterministic, no
  timestamps, provenance in the header.
- A policy is formal when a runnable artifact could falsify it.
- Logs preserve *why* a position fell, not just the final position.
- Self-hosting acceptance, when it arrives: T1 output == T2 output.

THE CONSTANT ITSELF -- RESOLVED, two independent evidence classes:
  1. Forced by construction, THIS corpus's own recorded probes: the
    ANCHOR (unoptimized) compilation of c/15, c/16, cpp/15, cpp/16,
    rust/3, rust/4 uses the SAME operation via an IMMEDIATE, not a
    memory load -- `xor $0x80000000,%eax` (float) / `movabs
    $0x8000000000000000,%rcx; xor %rcx,%rax` (double) -- read
    directly off op_units_<lang>.json's own `anchor.mnem` field, no
    inference needed.
  2. Forced by construction, INDEPENDENTLY rebuilt: `float negf(float
    a){return -a;} double negd(double a){return -a;}`, compiled with
    this sandbox's own `gcc -O2` (this session has no clang/rustc/go/
    swiftc -- the Airlock container that built the original probes is
    not reachable from here; this is the honest substitute, and IEEE
    754's sign-bit position is architecture/compiler-independent, so
    a different C compiler at the same optimization tier is not a
    weaker source for THIS specific fact). `objdump -s -j
    .rodata.cst16` on the resulting object: bytes `00 00 00 80 ...`
    (float, offset 0) and `00 00 00 00 00 00 00 80 ...` (double,
    offset 0x10) -- little-endian 0x80000000 / 0x8000000000000000,
    matching (1) exactly.
  Go's own anchor (go/9,10) still uses a memory load at a DIFFERENT
  rip offset (not an immediate) and swift's anchor is a bare `call`
  -- neither directly confirms the constant on its own, but IEEE 754
  admits no other correct value for this operation, and (1)+(2)
  already give two independent forced-by-construction confirmations
  from three different compilers (gcc, clang -- via this corpus's own
  c/cpp anchors -- and rustc's anchor) agreeing exactly.

THE ACTUAL BLOCKER, found while trying to RENDER, not just resolve,
the constant: gen7/gen11/gen12's entire register model is GP-INTEGER
ONLY. `REGMAP` (canon7_render.py) has no xmm0/xmm1/... entries at
all; `Context.operand_widths` tracks "a"/"b" as GP leaf widths;
nothing in the renderer knows how to emit `movss`/`movsd`/`movd`/
`movq`/`xorps`/`xorpd`, or to treat %xmm0/%xmm1 as the designated
argument registers a float-typed unit's real ship code actually uses.
Even with the constant known, THERE IS NO RENDERING PATH THAT CAN USE
IT -- rendering `-a` (float) requires the SAME float/XMM register
plumbing STAGE 5 must build for `ucomisd`/`ucomiss` condition codes
and packed/scalar float arithmetic. Building a second, narrower,
throwaway version of that plumbing just for this stage would
duplicate STAGE 5's own work rather than feed it.

DECISION, stated honestly: STAGE 3 converges ZERO units this lap.

- 2026-09-15: THE WIDTH RULE BY THE DEFINITION'S OWN USE, coded (the owner's decision of 2026-09-15, answering the width question log 284 §10 left open). The rule as it stood demanded 64-bit holders for every key, on the ground that a definition's operands are register reads; that is wrong for the W forms, whose text reads only the low 32 bits of each register and sign-extends a 32-bit result, so their operand width IS 32 and the arch-units equal to them are held at 32-bit holders. THE RULE: a definition's operand width, per read, is the width the definition's own subterm uses of that read, read off the subterm's own text — a read sliced from bit 0 by literal bounds is used at the slice's width (`extractLsb a 31 0` is a use of 32 bits of a), a read used whole is used at the register's width, a read used both ways is used whole; a slice whose high bound is written in the architecture's own parameters (the masking a 64-bit shift applies to its amount) is not a width read off the expression and the read keeps 64. `operand_widths` in `leanpath/operator_for.py` derives them from the key's own text when the key is built; every candidate and every table entry carries `operand_widths`, and the written table carries them beside the keys; `render` takes an arch-unit for a key when the arch-unit's holder widths EQUAL them. Result widths need no rule: a definition's result is the register. Nothing is keyed by a name.

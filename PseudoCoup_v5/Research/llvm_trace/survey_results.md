# LLVM x86-64 generated-code grammar survey

Methodology matches `DevComms/project_state.md` 2026-07-25 "GROUND
TRUTH" entry (Cranelift `assembler.rs` survey): count total lines,
comment/blank vs code, classify every code line into a syntactic
shape bucket with a script, report UNCLASSIFIED count, and separate
readable code from dense table-data initializers.

Script: `Research/llvm_trace/survey_inc.py`
(run: `python3 survey_inc.py <file.inc>`)

## Task 1 — X86GenMCCodeEmitter.inc: not a bug, wrong assumption

`fetch_llvm.sh`'s `run_tblgen -gen-emitter X86GenMCCodeEmitter.inc`
was based on the assumption that X86 byte-encoding is tblgen-generated
like Cranelift's `cranelift-assembler-x64`. It is not. Evidence:

- `llvm/lib/Target/X86/CMakeLists.txt` lines 5-21 list every
  `tablegen(...)` call the real X86 build performs:
  ```
  tablegen(LLVM X86GenAsmMatcher.inc -gen-asm-matcher)
  tablegen(LLVM X86GenAsmWriter.inc -gen-asm-writer)
  tablegen(LLVM X86GenAsmWriter1.inc -gen-asm-writer -asmwriternum=1)
  tablegen(LLVM X86GenCallingConv.inc -gen-callingconv)
  tablegen(LLVM X86GenDAGISel.inc -gen-dag-isel)
  tablegen(LLVM X86GenDisassemblerTables.inc -gen-disassembler)
  tablegen(LLVM X86GenInstrMapping.inc -gen-x86-instr-mapping)
  tablegen(LLVM X86GenExegesis.inc -gen-exegesis)
  tablegen(LLVM X86GenFastISel.inc -gen-fast-isel)
  tablegen(LLVM X86GenGlobalISel.inc -gen-global-isel)
  tablegen(LLVM X86GenInstrInfo.inc -gen-instr-info ...)
  tablegen(LLVM X86GenMnemonicTables.inc -gen-x86-mnemonic-tables -asmwriternum=1)
  tablegen(LLVM X86GenRegisterBank.inc -gen-register-bank)
  tablegen(LLVM X86GenRegisterInfo.inc -gen-register-info)
  tablegen(LLVM X86GenSubtargetInfo.inc -gen-subtarget)
  tablegen(LLVM X86GenFoldTables.inc -gen-x86-fold-tables -asmwriternum=1)
  ```
  There is no `-gen-emitter` call anywhere in the X86 backend
  (`grep -rn "tablegen(" llvm/lib/Target/X86/` finds only these 16,
  all in the one CMakeLists.txt — confirmed recursively, no other
  CMakeLists under `Target/X86` has a `tablegen()` call).
- `llvm/lib/Target/X86/MCTargetDesc/X86MCCodeEmitter.cpp` (2033 lines)
  `#include`s only hand-written headers
  (`X86BaseInfo.h`, `X86FixupKinds.h`, `X86MCAsmInfo.h`,
  `X86MCTargetDesc.h`, plus generic `llvm/MC/*.h`) — **no generated
  `.inc` file is included.**
- Its `MCTargetDesc/CMakeLists.txt` lists `X86MCCodeEmitter.cpp` as a
  plain source file, no tablegen dependency.
- Every emission routine (`emitImmediate`, `emitRegModRMByte`,
  `emitSIBByte`, `emitMemModRMByte`, `emitSegmentOverridePrefix`,
  `emitPrefix`, `encodeInstruction` at line 1555) is ordinary,
  hand-written C++ that reads `TSFlags`/`MCInstrDesc` bitfields
  (themselves generated data, see Task 4) and computes REX/ModRM/SIB
  bytes procedurally, not from a generated byte-string table.

**Conclusion: `-gen-emitter` is not used by the real X86 target at
all.** The earlier tblgen failure (`X86InstrMisc.td:1041:5: error:
Record 'AAA' does not have a field named 'Inst'!`) is explained by
this — `-gen-emitter` (the `CodeEmitterGen` backend, LLVM's generic
`Inst{}` bit-pattern encoder used by targets like AArch64/RISCV) tries
to read an `Inst` bit-pattern field that many X86 `.td` records
(e.g. `AAA`) never define, because X86 doesn't use that backend and
therefore never had to keep those records `-gen-emitter`-clean. No
fix was attempted or needed — this is not a broken invocation, it's
evidence that X86 encoding is categorically hand-written. No
`X86GenMCCodeEmitter.inc` exists or should exist.

## Task 2 — per-file survey

| file | total lines | blank | comment | code lines | UNCLASSIFIED | UNCLASSIFIED % |
|---|---|---|---|---|---|---|
| Cranelift `assembler.rs` (given, ground truth) | 14,876 (body) / 9.3 MB | — | — | — | **0** | 0% |
| `X86GenDAGISel.inc` | 375,884 | 263 | 67,809 | 307,812 | 357 | **0.095%** |
| `X86GenInstrInfo.inc` | 162,160 | 57 | 22,330 | 139,773 | 92 | **0.057%** |

Both LLVM files have non-zero unclassified lines, unlike Cranelift's
zero. The unclassified residue in both cases is small and is almost
entirely (a) the file-header comment block (`|* ... *|` box-comment
style my classifier didn't special-case) and (b) a short tail of
genuinely hand-shaped C++ helper functions embedded at the end of
each generated file (predicate-check bodies in DAGISel; instruction
name/lookup helpers and `isThreeOperandsLEA` in InstrInfo). These are
small in count but are qualitatively different from Cranelift's
uniform 12-shape grammar: they are free-form C++ (nested boolean
expressions, member-init lists), not fixed shapes.

Shape-kind counts (see raw script output for full breakdown):
- `X86GenDAGISel.inc`: 14 distinct shape buckets fully cover 99.9%
  of lines. Dominant buckets: `matcher_opcode_row` (247,885 lines,
  lines containing an `OPC_*` interpreter mnemonic) and
  `numeric_data_row` (52,281 lines, pure literal/enum-ref lists) —
  together **79.8%** of all lines. Real control flow
  (`if_stmt` 65, `switch_case` 441, `return_stmt` 157,
  `func_decl_def` 3) is negligible: well under 0.2% of lines.
- `X86GenInstrInfo.inc`: dominant buckets are `numeric_data_row`
  (69,692), `struct_init_row` (23,532, `MCInstrDesc`
  aggregate-initializer rows), `enum_member_row` (24,980, the
  `enum { ... }` opcode-numbering block), and `string_table_row`
  (21,266, the packed mnemonic string table) — together **86.7%** of
  lines. Real control flow is a handful of lines (16 `return`, 7
  `if`, 44 `switch/case`), concentrated in the ~230-line
  `X86GenInstrInfo` constructor/helper tail at the end of the file.

**Readable code vs dense table data:** by this line-level measure,
roughly **80-90% of both files is data-table content** (matcher
bytecode / struct-initializer rows / enum lists / string tables), and
under **1% is control-flow/function code** in the ordinary sense —
the opposite ratio from Cranelift's `assembler.rs`, which was reported
as ~1071 uniform, individually-readable `encode()` functions with
zero arithmetic and a closed 12-shape grammar throughout, not a
byte-table.

**The interpreter that reads the table (Task 2, DAGISel):**
`llvm/lib/CodeGen/SelectionDAG/SelectionDAGISel.cpp:3240`,
`void SelectionDAGISel::SelectCodeCommon(SDNode *NodeToMatch, const
unsigned char *MatcherTable, unsigned TableSize)` — a hand-written,
~1,147-line bytecode interpreter (measured via
`awk '/void SelectionDAGISel::SelectCodeCommon/,/^}/'` on the .cpp)
that walks the `MatcherTable` byte array declared inside
`X86GenDAGISel.inc`'s `SelectCode()` (opcodes `OPC_Scope`,
`OPC_CheckOpcode`, `OPC_MorphNodeTo*`, etc. — 138 distinct `OPC_*`
mnemonics found in the file, see below). Declared in
`llvm/include/llvm/CodeGen/SelectionDAGISel.h:452`.

## Task 3 — table-driven matcher vs hand-written C++ split

**Line/entry-count evidence (X86GenDAGISel.inc):**
- Total lines: 375,884. `MatcherTable[]` array spans lines 58-374,160
  (comment declares "Total Array size is 709928 bytes" at line
  374,160) — i.e. **~374,100 lines (99.5% of the file)** are the
  single dense byte array (with per-entry offset/decoding comments).
  The remaining ~1,700 lines (374,212-375,884) are hand-shaped-looking
  but still tblgen-generated predicate dispatch functions
  (`CheckPatternPredicate`, `CheckNodePredicate`,
  `CheckComplexPattern`), which are themselves large `switch`
  statements over predicate IDs, not free-form logic.
- Distinct `TARGET_VAL(X86::...)` instruction targets referenced from
  the matcher table (i.e. instructions selectable purely via the
  table): `grep -o "TARGET_VAL(X86::[A-Za-z0-9_]*)" X86GenDAGISel.inc
  | sort -u | wc -l` → **17,662** distinct target instructions
  (of 22,335 total instructions defined in `X86GenInstrInfo.inc`,
  `MCInstrDesc Insts[22335]`).
- Total selection actions (`OPC_MorphNodeTo*` / `OPC_EmitNode*` /
  `OPC_CompleteMatch` occurrences, i.e. individual matcher-table
  outcomes, not deduplicated by target instruction):
  `grep -oE "OPC_(MorphNodeTo|EmitNode|CompleteMatch)[0-9]*"
  X86GenDAGISel.inc | wc -l` → **32,066**.
- 138 distinct `OPC_*` interpreter mnemonics total (the full
  "instruction set" of the table-interpreter bytecode) —
  `grep -oE "OPC_[A-Za-z0-9_]+" X86GenDAGISel.inc | sort -u | wc -l`.

**Hand-written C++ selection (X86ISelDAGToDAG.cpp, 6,790 lines):**
- `X86DAGToDAGISel::Select(SDNode *Node)` (starts line 5,143) is a
  giant hand-written `switch (Opcode)` over `ISD::*`/`X86ISD::*`
  opcode kinds: `grep -c "case ISD::\|case X86ISD::"
  X86ISelDAGToDAG.cpp` → **210** hand-matched top-level cases (covers
  intrinsics, atomic ops, div/rem, shift-by-parts, LEA folding,
  vector select, etc.). Every case that doesn't match falls through
  `default: break;` at the end of the function to
  `SelectCode(Node)` (line 6,753) — the generated-table path.
- The specific claim under dispute — IDIV64r — is confirmed
  hand-selected in C++, **not** present in the generated table:
  - `grep -c "IDIV64r" X86GenDAGISel.inc` → **0**.
  - `X86ISelDAGToDAG.cpp:5918`: `case MVT::i64: ROpc = X86::IDIV64r;
    MOpc = X86::IDIV64m; break;` inside the hand-written div/rem
    lowering block (`X86DAGToDAGISel::Select`, `ISD::SDIVREM`/
    `ISD::UDIVREM` case), used later at line ~6023
    (`CurDAG->getMachineNode(ROpc, dl, MVT::Glue, N1, InGlue)`).

**Verdict on the retraction:** both claims are correct for different
parts of the pipeline and are not contradictory. The **bulk of X86
instruction selection by line count and by distinct-instruction
count is table-driven** (17,662 of 22,335 instructions reachable
purely via `MatcherTable`, 99.5% of the generated file is table data,
interpreted by one 1,147-line hand-written state machine). But a
**materially sized, hand-written escape hatch exists** (210
top-level `case` arms in `X86DAGToDAGISel::Select`, of which
div/rem, shift-by-parts, atomics, and certain intrinsics are
examples) that bypasses the table entirely for specific opcode
patterns, IDIV64r being one confirmed instance. Both are "true" — the
first claim describes the dominant mechanism, the retraction
correctly identifies that it is not universal.

**Uncertainty (labeled ESTIMATE):** the 210 `case ISD::`/`case
X86ISD::` count includes some cases that still partially delegate to
generated helpers/tables (e.g. complex-pattern matching functions,
themselves partly generated — see `CheckComplexPattern` at
`X86GenDAGISel.inc:375496`), so "210 opcodes hand-selected" overstates
how much logic is genuinely free-hand vs. how much is
hand-written-orchestration-over-generated-helpers. The true
proportion of x86 *instructions* (not opcode-kinds) selected via
hand-written code vs table is not counted exactly here — 17,662 is a
lower bound on table-reachable instructions, not a partition, since
some instructions may be reachable via both paths depending on
subtarget/pattern predicates. Treat "210" and "17,662 vs handful" as
ESTIMATEs of relative magnitude, not exact partitions.

## Task 4 — encoder path

Encoding is **100% hand-written C++**, no generated tables of the
Cranelift kind:
- `llvm/lib/Target/X86/MCTargetDesc/X86MCCodeEmitter.cpp`, 2,033
  lines, no generated `.inc` include (see Task 1 evidence).
- Key hand-written functions and line counts (grep line numbers):
  `getX86RegNum` (523), `getX86RegEncoding` (527), `emitImmediate`
  (532), `emitRegModRMByte` (603), `emitSIBByte` (609),
  `emitMemModRMByte` (615), `emitSegmentOverridePrefix` (1460),
  `emitPrefix` (1535), `encodeInstruction` (1555, the top-level
  entry point, ~478 lines to EOF).
- These functions do consult **generated data**: `MCInstrDesc`
  bitfields (`TSFlags`) from `X86GenInstrInfo.inc`'s
  `X86InstrTable::Insts[22335]` array (opcode class, operand-encoding
  form, REX/VEX/EVEX shape bits, etc. packed into a 64-bit `TSFlags`
  field per instruction — visible in the `struct_init_row` rows of
  Task 2, e.g. `0|(1ULL<<MCID::MayLoad)|... , 0x80002056ULL`). So the
  **byte values themselves are computed procedurally** by hand-written
  C++ that switches on those generated bitfield/enum values, unlike
  Cranelift where `assembler.rs`'s generated `encode()` functions
  emit the literal bytes directly.
- Split: 0 generated encoder lines (no `.inc` file exists), 2,033
  hand-written lines drive the entire encode step, consuming
  ~140,000 lines of generated *instruction metadata* (not encoder
  code) as lookup input.

## Verdict

**Not transpilable by the same tool approach as Cranelift's
`assembler.rs`.** Cranelift's grammar was closed, uniform, zero
arithmetic, and directly emitted final bytes per-instruction as
individually readable functions — ideal for a syntax-directed
transpiler. LLVM's X86 generated code is architecturally different in
a way that blocks the same approach:

1. **DAGISel (`X86GenDAGISel.inc`) is not a set of per-instruction
   functions at all.** It is a single ~700KB opaque byte array
   (`MatcherTable`) interpreted at runtime by a 1,147-line
   hand-written bytecode VM (`SelectCodeCommon`). There is nothing to
   "transpile" per instruction — the semantics live in the
   interaction between the byte stream and the interpreter's control
   flow (backtracking `OPC_Scope`, `OPC_SwitchOpcode`/`OPC_SwitchType`
   dispatch, glue/chain bookkeeping). A transpiler would have to
   reimplement the interpreter, not transliterate generated code.
2. **Selection is not table-only.** 210 hand-written `case` arms in
   `X86ISelDAGToDAG.cpp::Select()` bypass the table for specific
   opcodes (confirmed for IDIV64r), meaning correct behavior requires
   porting hand-written, non-generated logic as well — this has no
   analogue in the Cranelift slice, which was "nothing hand-written."
3. **The encoder has no generated component to transpile.** X86 byte
   encoding is categorically hand-written procedural C++
   (`X86MCCodeEmitter.cpp`), consuming generated *metadata* (bitfield
   tables) but computing bytes with real arithmetic/branching, unlike
   Cranelift's generated `encode()` functions which emit literal
   bytes with no arithmetic. There is no `X86GenMCCodeEmitter.inc`
   and none should be expected — `-gen-emitter` is simply not part of
   the real X86 build.
4. Even where a formal grammar exists (`X86GenInstrInfo.inc`'s
   struct/enum/string tables), it's ~87% dense data feeding a
   hand-written consumer (`InitMCInstrInfo`, `X86MCCodeEmitter`, etc.)
   rather than being executable code in its own right.

In short: Cranelift generates *code*; LLVM's X86 backend generates
*data* consumed by a small number of hand-written, general-purpose
interpreters, with additional hand-written escape-hatch logic
layered on top. A transpiler for LLVM would need to target the
interpreter + hand-written C++ (a much larger, more heterogeneous
surface — thousands of lines of free-form C++ across
`X86ISelDAGToDAG.cpp`, `X86ISelLowering.cpp` (62,204 lines,
unsurveyed in detail here), and `X86MCCodeEmitter.cpp`), not the
generated `.inc` files themselves.

## Unverified / uncertain

- `X86ISelLowering.cpp` (62,204 lines) was not surveyed in the same
  per-line-shape detail as the three `.inc`-adjacent files — only
  confirmed to exist and hand-written by inspection of includes; no
  shape/table split was computed for it. Given its size, this is a
  meaningful gap: any real transpilation effort would need to survey
  it too, and this report does not quantify how much of its logic is
  "instruction lowering as generic legal-graph rewriting" (closer to
  Cranelift's ISLE lowering layer) vs raw C++ heuristics.
- `X86GenGlobalISel.inc`, `X86GenFastISel.inc`,
  `X86GenAsmMatcher.inc`, `X86GenDisassemblerTables.inc`, etc. — the
  other tblgen backends visible in CMakeLists.txt — were not
  generated or surveyed; they exist but are out of scope per the
  original task list (DAGISel + InstrInfo + attempted MCCodeEmitter
  only).
- The 210-case count for `X86DAGToDAGISel::Select` is a raw grep of
  `case ISD::`/`case X86ISD::` and includes nested `switch`
  statements inside outer cases (e.g. the `INTRINSIC_W_CHAIN` case
  seen at the top of the function contains its own nested `switch
  (IntNo)`); the true count of *top-level* opcode dispatch arms is
  somewhat lower than 210, not separately isolated here — labeled
  ESTIMATE in Task 3.
- Whether any of the 17,662 table-reachable instructions overlap with
  the 210 hand-selected opcode kinds (i.e., same instruction
  reachable both ways depending on operand/subtarget predicates) was
  not checked; the "table vs hand-written" split is presented as two
  separate measurements, not a verified partition of the full
  instruction set.
- `check_resources.sh` in `Research/llvm_trace/` was not re-run as
  part of this survey; only `fetch_llvm.sh`'s `run_tblgen` function
  and the CMakeLists.txt ground truth were consulted directly.

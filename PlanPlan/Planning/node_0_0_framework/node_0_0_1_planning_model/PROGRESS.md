# PROGRESS — planning_model

- 2026-08-02 **done and exercised**: `read_frontmatter` rewritten to
  read a nested block, which PROTOCOL §1's `super_node` and
  `sub_nodes` require and the old line-splitter could not do.
  - **The old behaviour is preserved exactly.** A key with a value on
    its own line still reads back as the raw string to the right of
    the colon; only a key with an EMPTY value followed by indented
    lines becomes a dict or a list of dicts. That split is what let
    the reader change without touching anything built on it.
  - Measured after the change: `check_plans.py` gives the same 0
    errors and 5 warnings over the four line trees and 0/0 over this
    one; `render_plan.py` reports 0 grammar problems on all five trees
    (4, 8, 10, 18 and 12 nodes); the 52 dashboards regenerate to the
    same hash as before the change, `0610c73c10c32a956973969404abe6d4`,
    and the four line repos come back 0 dirty.
  - Exercised on each shape: old-style frontmatter reads back
    unchanged; the new shape parses both fields including a cross-repo
    edge whose `remote` value contains its own colons; `super_node:
    null` and `sub_nodes: []` are distinguished from the fields being
    absent, so a leaf stated on purpose is not confused with a CORE
    that never had the field.
  - Three malformed shapes were checked to be REPORTED rather than
    repaired — an entry missing `path`, an entry carrying an unknown
    key, and a `sub_nodes` written as an inline dictionary. Each
    returns `malformed`. A missing `path` and a misspelled `path` are
    the same defect, and guessing at either is how a wrong edge
    survives.
  - Added alongside: `parse_edge` and `parse_edge_register`, and four
    attributes on `PlanningNode` — `super_edge`, `super_edge_status`,
    `sub_edges`, `sub_edges_status`. Nothing reads them yet; the
    checks that will are the next step.

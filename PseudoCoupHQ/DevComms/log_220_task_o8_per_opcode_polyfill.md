# 1. What the objects are

- **a single-opcode unit** — one row of task o2's
  (`PseudoCoupHQ/Research/oracle/arch_opcodes/single_opcode_units.json`,
  log 208) `single_opcode_groups.<lang>.narrow`: a group of arch-units,
  across c/cpp/go/rust/swift, whose body with `ret` and plain register
  moves stripped is exactly ONE arch opcode, holding one
  `example_unit_id` and the group's own machine body bytes.
- **a proved term** — that example unit's own `layer5_normalized_text`
  from `Research/op_pipeline/term66_store`, read only where
  `outcome == "PROVED_ON_SHIP"`; a row whose unit carries no such term
  is listed and skipped, never polyfilled.
- **a polyfill** — a c function whose body is that term written in c's
  own operators, produced by task o7's ONE renderer (`emulate.Renderer`,
  imported unchanged) from the z3 term; a term the renderer cannot
  render is refused by cause, exactly as o7 refuses.
- **the collapse test** — compile the polyfill at the flags the whole
  c corpus was built with (o7's own `emulate.compile_and_carve`,
  imported unchanged), carve the body, and ask:
  Q0 (NEW to this task) — strip the carved body's chaff by task o2's
  own narrow rule (`single_opcode_units.strip_chaff`, imported
  unchanged); if exactly one opcode remains and it is the row's OWN
  mnemonic, LANDED; one opcode but a DIFFERENT mnemonic,
  LANDED_ELSEWHERE (named); more than one opcode (or none — a
  sub-case named separately, §3b), NOT_COLLAPSED.
  Q1 — byte identity, here against the ROW's OWN body (o7 asked this
  against the whole c corpus; this task's comparison scope is the one
  body the row was drawn from).
  Q3 — does the gate (`emulate.prove_against_x`, imported unchanged,
  3,000 ms) prove the polyfill's body equal to the row's own example
  unit's body, for every input.

# 2. What was done and what came back

the owner asked (2026-09-06, quoted in the brief): "im curious if we could
auto-polyfill for each unique arch opcode at a high level. and im
curious is the compiler will optimally lower it to the correct arch
opcode." Task o7 (log 218) asked a related but different question —
does a c emulation of a GO/RUST/SWIFT unit's term collapse to a c unit
the corpus already has. This task asks it the way the owner framed it here:
per unique arch opcode, per language, does the compiler's own
optimizer land the polyfill back on the SAME opcode the unit was
chosen to represent.

For every row of task o2's five-language single-opcode population
(259 rows: c 83, cpp 82, rust 48, go 27, swift 19), the row's own
example unit's proved term was rendered to c by o7's renderer,
compiled by clang at `-std=c17 -O1` (the corpus's ship build), carved,
and chaff-stripped by o2's own narrow rule. 243 of 259 rows had a
proved term to work from (16 skipped, all c/cpp `call` rows built
around wide-integer runtime callees — `__divti3`/`__udivti3`/
`__modti3` — whose term66_store record carries no `PROVED_ON_SHIP`
outcome); 217 of 243 rendered and compiled; 26 were refused, all for
one cause (§7).

**Q0, the question the owner asked directly:** 197 of 217 (91%) LANDED — the
polyfill's chaff-stripped body came back as exactly the row's own
mnemonic. 2 of 217 LANDED_ELSEWHERE — both `go/add` rows, where clang
chose `lea` over `add` for a two-register sum (§6.2). 18 of 217
NOT_COLLAPSED — more than one opcode remained (5 of those 18 are a
distinct sub-case, §3b: the remaining opcode count is ZERO, not
plural, because the row's own body is a pointer store the term
machinery's scalar answer does not carry).

**Q1, byte identity against the row's own body:** 155 of 217 (71%).
This is a stronger rate than o7's whole-corpus Q1 (5 of 204) because
the comparison scope here is narrower and deliberately favourable —
this row's own body specifically, not the whole corpus — so the two
numbers are not read against each other.

**Q3, the gate's proof against the row's own example unit:** 216 of
217 (99.5%) PROVED_ON_SHIP; 1 DISPROVED on its first pose, PROVED once
its narrow argument is zero-extended from its holder width (§3c) — the
same caller-extension rescue o7's own Q3 used.

## 6.2 LANDED_ELSEWHERE

Row `go/add`, example unit `go/op_312`. The term, **LITERAL**:
`Extract(31, 0, v0) + Extract(31, 0, v1)`.

The two bodies, **LITERAL**:

| side | body |
|---|---|
| the row's own body (`add`) | `add %ebx,%eax; ret` |
| the polyfill (`lea`) | `lea (%rdi,%rsi,1),%eax; ret` |

Verdicts: Q0 `LANDED_ELSEWHERE` (landed on `lea`); Q3 `PROVED_ON_SHIP`.

**GLOSS.** Both bodies answer the same term — a two-register 32-bit
sum. go's own compiled unit used `add`; clang, given the polyfill's
c source for the identical sum, chose `lea (%rdi,%rsi,1),%eax` — the
address-computation instruction doing addition as a side effect
without touching the flags register `add` would set. This is the owner's
"is it possible the compiler simplifies down to the direct
equivalent" question answered at its most literal: the compiler DID
find the arch-unit's own semantic content, but "the same opcode" and
"an equally valid opcode for the same computation" are different
readings of "correct," and this row is the case where they diverge.

## 6.3 NOT_COLLAPSED

Row `c/or`, example unit `c/op_365`, 4 opcodes remaining after the
narrow chaff strip. The term, **LITERAL**:
`Concat(Extract(63, 32, v0), Extract(31, 0, v0) | Extract(31, 0, v1))`.

The polyfill's carved body, **LITERAL**:
`movabs $0xffffffff00000000,%rax; and %rdi,%rax; or %esi,%edi; or %rdi,%rax; ret`.

Verdicts: Q0 `NOT_COLLAPSED` (4); Q1 `BYTES_DIFFER`; Q3
`PROVED_ON_SHIP`.

**GLOSS.** The row's own body is `mov %esi,%eax; or %rdi,%rax; ret` —
a single 64-bit `or` that happens to leave the high 32 bits of the
64-bit answer equal to the high 32 bits of `v0` because ORing a
zero-extended 32-bit value changes nothing above bit 31. The term as
WRITTEN is more general than that: it concatenates `v0`'s own high
half back on explicitly, rather than relying on the zero-extension the
row's body gets for free from `mov %esi,%eax`. clang proved the two
equal (Q3), but did not find the row's own one-instruction shortcut
from the term's more literal four-instruction statement of it.
